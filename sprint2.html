🔐 Authentication: Keycloak Sign-in (PBI3)

หัวใจสำคัญคือ “Browser เป็นคน login กับ Keycloak เอง — Backend ไม่เคยเห็นรหัสผ่าน” โดยใช้โปรโตคอล OpenID Connect (Authorization Code Flow + PKCE S256)

FRONTENDindex.html

ผู้ใช้คลิกลิงก์ <a href="./my-schedule.html">My Schedule</a> — หน้า index.html ไม่เคยโหลด keycloak.js เลย เพื่อไม่ให้กระทบ PBI1–2

AUTHjs/my-schedule-main.js → js/auth.js

เรียก await requireSignIn() ซึ่งรัน keycloak.init({ onLoad: 'login-required', pkceMethod: 'S256', checkLoginIframe: false })

KEYCLOAK

ถ้ายังไม่ login → keycloak-js สร้าง code challenge (PKCE) แล้ว redirect เบราว์เซอร์ไปหน้า login ของ Keycloak ที่ bscit.sit.kmutt.ac.th/intproj26/keycloak/

AUTHjs/auth.js

กรอกรหัสนักศึกษา/อาจารย์สำเร็จ → Keycloak redirect กลับมา my-schedule.html?code=... → keycloak-js เอา code ไปแลกเป็น Access Token (JWT) อัตโนมัติ แล้วแกะ tokenParsed ส่งคืน { username, name, roles }

FRONTENDmy-schedule-main.js

โชว์ชื่อเต็มบน header, เปิดใช้งานปุ่ม Sign Out (ซึ่งเรียก keycloak.logout({ redirectUri: './' }) เพื่อเคลียร์ session บน Keycloak แล้วกลับหน้าแรก) จากนั้นยิง API ด้วย user.username

ทางเลือกอื่น: จัดการ OIDC / Login แบบอื่น

ข้อดี
  • ตรงกับ Keycloak ของวิชา มี sample ให้เลย
  • ไม่ต้องมี build step (copy 2 ไฟล์ลง vendor/)
  • จัดการ PKCE + token refresh ให้ครบ
ข้อเสีย
  • ผูกกับ Keycloak โดยเฉพาะ (เปลี่ยน Identity Provider ต้องแก้)

เหมาะกับโปรเจกต์ที่อยากไม่ผูกติดกับ Keycloak (vendor-neutral)

ให้ Backend เป็นคนแลก code กับ Keycloak แล้วออก HttpOnly; Secure Session Cookie ให้ Browser — ปลอดภัยกว่าเพราะ JavaScript อ่าน token ไม่ได้ (กัน XSS ขโมย token) แต่ซับซ้อนกว่าและไม่ตรงกับสเปกวิชาที่ให้ Frontend ส่ง Bearer token

🎨 Frontend: my-schedule.html และ State Management

ต่างจากหน้าแรกที่มีแค่ตารางเดียว หน้า my-schedule.html ต้องจัดการ 2 ตารางที่สัมพันธ์กัน + 3 Dialog + State ในหน่วยความจำ เพื่อไม่ให้ยิง API ซ้ำ (TR-06)

1) โหลดข้อมูลเริ่มต้น 3 เส้น (ทำครั้งเดียว)

2) อัปเดตตารางหลัง Select / Remove / Change โดยไม่ Refetch

แนวคิดแบบ Single Source of Truth: schedules (ข้อมูลทั้งชั้นปี) + selections (รายการที่เลือก) คือ state กลาง — พอ API ตอบสำเร็จ เราแก้แค่ array selections ใน JS แล้วเรียก renderStudentTables() วาด 2 ตารางใหม่ทันที!

💡 เมื่อไหร่ถึงจะยิง fetchStudentSelections ใหม่? เฉพาะตอนที่เกิด 409 (already-selected) หรือ 404 — เพราะแปลว่าข้อมูลบนหน้าจอ “ล้าสมัย” (เช่น เปิด 2 แท็บแล้วลบไปอีกแท็บ) พอผู้ใช้กด OK/Esc ปิด dialog ค่อยยิงขอ selections มาซิงก์ใหม่ให้ตรงกับ DB

3) ทำไมต้องใช้ <dialog> แทน alert() / confirm()?

ใน my-schedule-renderer.js มีฟังก์ชัน showMessageDialog() และ showChangeDialog() ที่คุมแท็ก <dialog> จริงบน DOM:

  • Playwright (และ automated tests) มองไม่เห็น window.alert()/confirm() เป็น DOM element แต่หา role="dialog" จาก <dialog>.showModal() ได้
  • แต่งหน้าตาให้เข้ากับธีมเว็บได้ (Liquid Glass) และใส่ radio buttons ใน Change dialog ได้
  • ข้อควรระวัง (TC-PBI7-7): ตอนเปิด Change dialog ต้องสร้าง radio จาก section อื่นที่ item.section !== currentSection ทุกครั้ง และปุ่ม Change ต้อง disabled = true จนกว่าจะเลือก radio

ทางเลือกอื่น: การเขียน Dialog แบบ Promise (async/await)

เข้าใจง่ายสำหรับคนคุ้นเคยกับ event handler แต่ถ้ามี dialog ซ้อนหลายชั้นโค้ดจะย่อหน้าลึกขึ้น

ข้อดี
  • อ่านจากบนลงล่าง ไม่ซ้อน callback
  • ลดความซ้ำซ้อนเวลาต้องเปิด clash dialog ต่อจาก change dialog
ข้อเสีย
  • ต้องระวังไม่ให้เปิดซ้อนกัน 2 อันพร้อมกัน
