Requirement ที่ต้องทำ

PBI1 · VIEW-ALL-SCHEDULE
  • PATH /intproj26/<TEAM>/
  • DISPLAY ตาราง Code, Title, Type, Section, Group, Day, Time, Weeks, Remarks (ไม่มี Room เพราะเป็นหน้า public)

PBI2 · VIEW-SCHEDULE-BY-YEAR-LEVEL
  • DISPLAY ปุ่ม All, Year 1 … Year 4 — ปุ่มที่เลือกมี aria-pressed="true"
  • BEHAVIOUR URL แสดงชั้นปีที่เลือก (?yearLevel=2) เปิด/รีโหลดแล้วยังคงค่าเดิม
  • ห้าม reload และ ห้ามขอข้อมูลที่มีอยู่แล้วซ้ำ (TR-06)
  • API GET /api/v1/schedules?yearLevel=n (n = 1–4)
  • Should-have (ไม่ได้ทดสอบ): ปุ่ม Back/Forward คืนค่าที่เลือกก่อนหน้า

Prisma model — แผนที่จากตาราง SQL ไปเป็น object ใน JS

backend/prisma/schema.prisma บอก Prisma ว่าตารางหน้าตาอย่างไร ชื่อ snake_case ในฐานข้อมูลถูก map เป็น camelCase ด้วย @map

ทางเลือกอื่น: เก็บ “วัน” แบบไหนดี?

ใช้ ENUM('MONDAY',…,'SUNDAY') — MySQL เก็บ ENUM เป็นเลขลำดับภายใน ทำให้ ORDER BY day_of_week เรียง จันทร์ → อาทิตย์ ได้ทันที

ข้อดี
  • อ่านง่าย ค่าผิดใส่ไม่ได้
  • Prisma สร้าง enum ให้ใน JS
ข้อเสีย
  • เพิ่มค่าใหม่ต้อง ALTER TABLE
ข้อดี
  • เรียงลำดับ/คำนวณง่าย
ข้อเสีย
  • ต้องแปลงเป็น "TUESDAY" เองก่อนส่ง API
  • อ่านข้อมูลดิบแล้วไม่รู้ความหมาย
ข้อดี
  • Normalize เต็มรูปแบบ แก้ชื่อที่เดียว
ข้อเสีย
  • ต้อง JOIN เพิ่ม — เกินความจำเป็นสำหรับ 7 ค่าที่ไม่เปลี่ยน

⚙️ Backend: จาก server.js ถึง JSON

1) จุดเริ่มต้น — server.js และ app.js

แยก 2 ไฟล์เพื่อให้ app (ตัว Express) import ไปทดสอบได้โดยไม่ต้องเปิด port

ทำไม import ด้วย .js และใช้ import แทน require? เพราะ package.json ตั้ง "type": "module" → Node ใช้ ES Modules ซึ่งต้องเขียนนามสกุลไฟล์เต็ม

2) Health check

ใช้ให้ระบบทดสอบของวิชาเช็คว่า backend “ยังหายใจอยู่” และเป็นของทีมไหน

3) Route → Controller → Service → Repository

นี่คือหัวใจของ Layered Architecture ที่ทีมใช้ทั้งโปรเจกต์ แต่ละชั้นมีหน้าที่เดียว:

routes/URL นี้ → middleware ไหน → controller ไหน
→
controllers/อ่าน req, ส่ง res, ส่ง error ให้ next()
→
services/logic: format + sort
→
repositories/query DB ผ่าน Prisma
🔎 สังเกต controllers/schedule.controller.js ยังอยู่ในโปรเจกต์ แต่ ไม่มีไฟล์ไหน import แล้ว — เป็นของ PBI1 เวอร์ชันแรก ก่อนถูกแทนด้วย schedule-filter.controller.js ที่รวม PBI1+2 ไว้ด้วยกัน (ลบทิ้งได้)

4) Formatter — ทำให้ตรง API contract

⚠️ จุดที่พลาดง่าย: “09:30 บนเครื่องเรา แต่ 02:30 บน server” ถ้าใช้ getHours() จะได้เวลาตาม timezone ของเครื่อง (ไทย +7) — ทีมใช้ getUTCHours() จึงได้ค่าเดียวกันทุกเครื่อง

ทางเลือกอื่น: แปลงเวลาที่ไหนดี?

Prisma อ่าน TIME มาเป็น Date แล้ว formatTime() แปลงเป็น string — ใช้ซ้ำได้ทั้ง schedules, sessions, clashes

ข้อดี
  • ไม่มีปัญหา timezone เลย
ข้อเสีย
  • ต้องเขียน SQL เอง เสียความ type-safe ของ Prisma
  • ต้องประกอบ object course ซ้อนเอง

สั้นกว่า และเป็น UTC เสมอเหมือนกัน

5) Sorter — เรียงลำดับ 6 ขั้นตาม PBI1

“Neither id order nor code order is the PBI1 order.” — ต้องเรียง Year level → course id → section → day (Mon first) → start time → schedule id

ทางเลือกอื่น: ให้ฐานข้อมูลเรียงให้

ข้อดี
  • ใช้ซ้ำกับข้อมูลที่ไม่ได้มาจาก query เดียว (เช่น lecturer schedules)
  • ทดสอบเป็น unit ได้ง่าย
ข้อเสีย
  • ต้องดึงทุกแถวมาก่อน (ไม่มีปัญหาที่ ~100 แถว)

FIELD() ใช้ได้แม้คอลัมน์จะเป็น VARCHAR ไม่ใช่ ENUM

6) Validate query ?yearLevel

ตอน Sprint 1 ทีมมีตัวตรวจง่าย ๆ ต่อมา Sprint 3 (PBI9) ยกระดับเป็น middleware/validate.js ที่ตอบ 400 แบบ RFC 9457

(relative)? เพราะเว็บจริงอยู่ใต้ path /intproj26/<TEAM-PATH>/ — ถ้าเขียน /api/v1 (ขึ้นต้นด้วย /) จะวิ่งไปที่ root ของโดเมนผิดที่ ส่วนตอนพัฒนาบนเครื่อง (port 5173/5500) frontend กับ backend อยู่คนละ port จึงชี้ไป http://localhost:3000 ตรง ๆ (และต้องเปิด cors() ที่ backend)
