💡 ทำไมต้องแยก Controller กับ Service ออกจากกัน?
  • Controller รู้จักโลกของ HTTP (req.params, req.body, res.status(201)) แต่ไม่รู้กฎธุรกิจ

Middleware Pipeline ใน student.routes.js

ลำดับ middleware ใน Express คือตัวกำหนดลำดับ Error 401 → 403 → 400 → 404 → 409 อัตโนมัติ! ลองดูโค้ดจริง:

🧠 ทำไมทีมใส่ express.json() แค่ใน POST/PUT หลัง requireSelf แทนที่จะใส่บนสุดใน app.js? ฉลาดมาก! เพราะถ้าใส่ app.use(express.json()) บนสุดใน app.js เมื่อมีคนส่ง JSON พัง + ไม่มี Token ตัว express.json() จะพ่น 400 ออกมาก่อน requireAccessToken จะได้ตรวจ 401 — ซึ่งจะ ผิดลำดับ 401 → 403 → 400 ของ PBI9! การวาง express.json() ไว้หลัง requireSelf ทำให้ 401 และ 403 ชนะ 400 เสมอ

ไฟล์เก่าที่ยังค้างอยู่ใน Repo (ไม่ได้ใช้งานแล้ว)

จากการไล่ import graph ทั้งโปรเจกต์ พบ 2 ไฟล์ที่เป็นร่องรอยจาก Sprint 1 ซึ่งปัจจุบัน ไม่มีไฟล์ไหน import แล้ว:

src/config/db.js

ไฟล์เชื่อมต่อ MySQL ด้วย mysql2/promise จากช่วงเริ่มต้น ก่อนที่ทีมจะเปลี่ยนมาใช้ Prisma ทั้งหมดใน src/config/prisma.js (รวมถึง dependency mysql2 ใน package.json ก็ไม่ได้ถูกเรียกในโค้ด runtime แล้ว)

src/controllers/schedule.controller.js

Controller ตัวแรกของ PBI1 ก่อนถูกแทนที่ด้วย schedule-filter.controller.js ที่รองรับทั้ง PBI1 (All) และ PBI2 (?yearLevel) ในไฟล์เดียว

แบบแบ่งตาม Layer (ที่ทีมใช้)
  • routes/, controllers/, services/, repositories/
  • หาง่ายว่า middleware หรือ formatter อยู่ไหน
  • เหมาะกับขนาดเล็ก-กลาง (5–15 endpoints)
แบบแบ่งตาม Feature (ทางเลือก)
  • features/students/ (รวม route+ctrl+svc+repo), features/lecturers/
  • แก้ 1 ฟีเจอร์ไม่ต้องสลับเปิด 4 โฟลเดอร์
  • เหมาะเมื่อโปรเจกต์โตเกิน 30–50 endpoints

Express 4 (ปัจจุบัน): ต้องเขียน try { ... } catch (err) { next(err); } ในทุก async controller ไม่งั้น unhandled rejection จะค้าง request
Express 5 / Fastify / Hono: จัดการ async error ให้อัตโนมัติโดยไม่ต้องเขียน try/catch ซ้ำทุกฟังก์ชัน และ Fastify/Hono มี schema validation ในตัว
